# Production Firebase migration

## Prerequisites

Target the existing `between-turns-paul` project and its current billing account. Confirm billing, current quotas, exact IAM changes, expected export/import and ongoing charges, and the maintenance window with Paul before provisioning. Save cloud inventory and deployment evidence outside Git. Keep all credentials, environment overrides, and data exports out of commits.

1. Inventory the six projects with authenticated Firebase and Google Cloud read commands. Record Hosting site IDs and live versions, active Functions revisions and service URLs, codebases, scheduler jobs, runtime accounts and effective IAM, Auth providers and domains, App Check registrations/enforcement, database IDs/locations, rules, indexes, TTL policies, and current routing. Confirm Horse Race has no live resources or data. Record a source-to-destination map and release IDs for rollback.
2. Compare the live hub and Rewards Functions configuration and deployed frontend assets with the branch. Preserve current lobby layout, sign-in behavior, endpoint contracts, reward inventory indexes, current games, and security headers. Capture current `APPS_JSON`, `GAMES_JSON` and `GAME_CLIENTS_JSON` from live configuration without printing the complete environment. Inventory any clients still dependent on legacy callable names or URLs.
3. Confirm availability of the five new site IDs in `.firebaserc`. If a site ID is taken, choose another globally unique ID and update the Firebase target, hub CSP, environment settings, and both registries consistently. The canonical new domains use `.web.app`.

## Destination staging

1. Create the five named Firestore Standard databases, corresponding Hosting sites, and same-project service accounts. Match each source database location when practical and approved. Keep the hub on its existing default database. Configure rules, indexes, and any live TTL settings for each database before importing. Use `npm run deploy -- all data --dry-run` to inspect the shared data deployment.
2. Give each runtime a conditional `roles/datastore.user` binding scoped to `projects/between-turns-paul/databases/DATABASE_ID` using exact `resource.name` equality. Keep the hub's required Firebase Auth user-read access scoped to the permissions it actually uses. Review direct and inherited permissions for broader database grants. Give Rewards and the four games service-level `roles/run.invoker` on the hub integration API. Give the game runtimes that use Rewards service-level invoker on the Rewards game API. Scheduler principals get invoker on their own scheduled service. Keep backend integration and scheduler endpoints private. Use the approved Cloud Run invoker mechanism on the browser-facing hub and Bingo callables and the five embedded HTTP endpoints. Keep Firebase Auth and App Check enforced on callable commands. Recheck transport and IAM after every Functions deployment because deployment may change Cloud Run settings.
3. Keep the hub Firebase Web App and Auth settings unchanged. Register the new Bingo Web App in the hub Firebase project, configure App Check for the new Bingo domain, and confirm Anonymous Auth works. Existing hub guest users stay in the same Auth project and browser origin. Old standalone Bingo anonymous users and browser-local cards stay on the old origin. Old standalone Bingo room records are retained by the data migration and new standalone sessions start fresh.
4. Create ignored `functions/.env.between-turns-paul` files using the app examples. Set exact runtime accounts, browser origins, backend endpoint URLs, and OIDC audiences as reported by the deployed services. The URL a caller uses for an ID-token request and the receiving function's configured audience must match. Preserve existing hub audience if its endpoint stays unchanged. Use the app's `.env.production.local` for public Firebase/App Check settings where required. Set `CUTOVER_WRITES_ENABLED=false` in new destination backends for staging. Inspect target selection with `--dry-run`, and use `--apply` for approved deployment. Stage the five replacement apps separately and leave the production hub serving its current clients. Check Hosting headers and HTTP maintenance responses before exposing the apps.

## Data migration and switch

1. Announce the standalone Bingo cutoff before the migration. Stop creating new standalone rooms during the drain window and give current sessions at least 24 hours before freezing the old backend. Confirm no live standalone rooms remain active or account for them before starting the export.
2. Prevent production writes and pause source Cloud Scheduler jobs. Put the hub and legacy browser transports in maintenance, remove unauthenticated invocation from legacy browser write services, suspend old backend invokers, and wait for in-flight requests to drain. Verify old methods cannot write and destination gates still reject writes. Preserve the hub's database and Auth records in place. Record the freeze time and all settings needed to re-enable the old applications.
3. Export each populated source Firestore database and import to its named destination with the approved, location-compatible storage and service-agent access. Use complete managed exports so document IDs, nested awards, activity, command and settlement receipts, and pending work survive. For each source and destination, compare counts by collection group and sampled records, with targeted checks of permanent Awards ownership, pending transfer and settlement linkage, and in-progress embedded runs. Keep export manifests and record import operation IDs. Use an empty Horse Race database if verified.
4. Build the destination hub release from the reconciled source. Merge current metadata and update each active app registration to its new origin and runtime. Set the Rewards embed URL and each game's catalog embed URL to the new site. Stage Horse Race with `ready: false`. Update Rewards game client identities while preserving game IDs and valid callback paths. Deploy the updated hub functions and Hosting during the same maintenance window. Verify the new CSP, routes, function IAM, and direct function status while gates are closed.
5. Reopen destination writers and enable destination maintenance after checking all app endpoints and the dependency routing. Verify hub Google sign-in and existing inventory, guest continuity, all game flows, and standalone Bingo with new accounts. Test Horse Race with a controlled session before making its catalog entry public. Check old schedulers and write endpoints are inactive. Publish the five new URLs. Monitor errors, scheduler health, and settlement backlogs after reopening.

## Recovery

Before accepting destination writes, restore the recorded source IAM, scheduler state, registry, and Hosting release if the cutover fails. Keep gates closed on the destination during that rollback. After accepting destination writes, serve recovery code against destination data and reconcile any pending commands from receipts. Keep source projects and exports available for recovery. Old URLs have no automatic redirect. Project deletion is a separate action.
